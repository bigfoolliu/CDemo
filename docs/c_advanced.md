# 深入 C 语言：从语法到工程约束

这些示例展示的不仅是语法，还包括接口契约、不变量、资源生命周期和失败处理。建议先学完基础示例，再按本页顺序阅读。运行 `make advanced` 执行全部进阶示例，运行 `make sanitize` 使用 AddressSanitizer 与 UndefinedBehaviorSanitizer 检查这些示例。

## 1. 动态数组：扩容与失败安全

源码：`src/advanced/01_vector.c`。

`Vector` 保存地址、长度、容量和分配回调。有效状态满足 `length <= capacity`，只有长度以内的元素已经初始化。容量按几何级数增长，连续插入的均摊成本为 O(1)，但某次扩容仍可能是 O(n)。

`reserve` 先验证大小乘法不会溢出，再将 `realloc` 的结果写入临时指针。只有成功后才更新容器，因此失败时仍可使用原数据。通过替换分配回调为 `fail_resize`，测试无需耗尽系统内存就能验证失败路径。

所有权由容器持有；直接复制结构体会形成两个指向同一块内存的所有者，容易重复释放。扩容还可能让外部保存的元素指针失效。`destroy` 释放内存并恢复空状态，因此可重复调用。

已验证：多次扩容保持全部元素、容量溢出拒绝、分配失败保持地址与内容、重复销毁。

练习：实现 `pop`、按索引删除和深复制；让分配器在第 N 次扩容失败，检查 `push` 失败后的长度。进一步设计独立的分配与释放接口，使容器支持真正的自定义内存池。

## 2. 严格整数解析：在发生溢出之前拒绝输入

源码：`src/advanced/02_parser.c`。

解析协议明确接受什么：十进制数字、一个可选正负号、无空白、无尾随字符。输出参数仅在成功时修改，错误分为空输入、语法错误和范围错误。若前缀已超范围，函数直接返回范围错误，不继续扫描剩余字符。

实现采用负数累积，因为 `INT_MIN` 的正数绝对值可能无法用 `int` 表示。每次乘以 10 之前先检查下界，再在减去下一位之前检查下界；不会先执行溢出运算再判断。

已验证：零、负零、正负数、空串、单独符号、非法字符、空白、`INT_MIN`、`INT_MAX`、超范围及失败时输出不变。

练习：支持前后空白或十六进制，明确新协议；增加超出 `INT_MIN` 的负数测试，与 `strtol` 对照验证。比较“不接受任何多余字符”与“允许解析前缀”的接口差异。

## 3. 二进制协议：零拷贝不等于强制转换结构体

源码：`src/advanced/03_binary_protocol.c`。

协议使用四字节头：版本、类型、两字节大端长度。解码器逐字节组合长度，并检查输入长度完全匹配。`length != size - 4` 在确认头部完整后执行，避免先计算加法造成溢出。

不能假设线上的数据结构与内存结构体布局相同：结构体可能有填充，机器字节序可能不同，输入地址可能未对齐，通过不同类型指针读数据还涉及对象访问规则。逐字节解码将这些约束显式化。

返回的载荷是借用视图，不分配、不复制；调用者不能在缓冲区失效后继续使用视图。载荷是二进制数据，不保证 NUL 结尾，不能直接按 C 字符串打印。空载荷指针位于尾后位置，不能解引用。

已验证：有效帧、所有截断长度、错误版本、空载荷及失败时输出不变。此格式要求八位字节，并使用标准的 `uint8_t` 类型。

练习：实现编码器和往返测试，增加超长帧测试，再设计流式解析器区分“需要更多数据”和“数据无效”。

## 4. 函数指针与上下文：可复用的算法接口

源码：`src/advanced/04_callbacks.c`。

遍历算法只负责枚举元素，回调实现实际操作。`void *context` 携带状态，既可累加，也可寻找最大值，无需全局变量。返回 `false` 允许提前停止，返回的计数只包含成功处理的元素。

上下文的实际类型必须与回调契约一致，不能因为使用 `void *` 就忽略类型与生命周期。示例为同步调用，不保存回调与上下文；异步接口必须另行定义它们的生命周期。

累加回调采用 `0 <= sum <= limit <= INT_MAX` 不变量，用 `value > limit - sum` 在加法前拒绝超限输入。最大值回调通过计数区分空状态，不依赖某个特殊初始值。

已验证：提前终止、全部遍历、空集合和最大整数边界。

练习：实现带上下文的过滤器，增加错误码与主动停止两种结果；考虑如何让公共 API 检查非法初始状态。

## 5. 原子操作：计数与发布是两个不同问题

源码：`src/advanced/05_atomics.c`。

两个线程对同一个原子计数器递增。`memory_order_relaxed` 保证原子增量不会丢失，但不用于保证其他对象的可见性。

生产者先写普通 `payload`，再用 release 存储 `ready=true`；消费者用 acquire 读取到该值后，才读取 `payload`。这一配对建立同步关系，使发布前的写入对消费者有序可见。若把这对操作都改成 relaxed，普通载荷访问将失去所需同步，不能用“本机运行正常”证明安全。

这是一次性发布协议：发布后生产者不再修改载荷。反复发布需要额外的消费确认或其他同步机制。线程退出后通过 join 回收线程资源，再检查最终计数。

`<stdatomic.h>` 是 C11 引入的 ISO C 标准设施；`pthread_create`、`pthread_join` 和 `sched_yield` 是 POSIX API，适用于当前 macOS 及常见 Linux 环境，需要 `-pthread`。原生 Windows 工具链需适配线程 API。原子操作不保证在所有实现上都是无锁的。

已验证：双线程总计 20000 次增量和发布值 42。ASan/UBSan 通过不代表并发正确性已被证明，也不能替代 ThreadSanitizer 或内存模型分析。示例等待采用自旋加让出 CPU，实际系统可考虑条件变量。

练习：增加生产者数量，明确共享对象的初始化和销毁时机；实现互斥锁版本，对比接口复杂度和性能。不要简单把一次性标志反复复用为消息队列。

参考：[WG14 内存模型说明](https://open-std.org/jtc1/sc22/wg14/www/docs/n1479.htm)、[POSIX pthread_create](https://pubs.opengroup.org/onlinepubs/000095399/functions/pthread_create.html)、[POSIX pthread_join](https://pubs.opengroup.org/onlinepubs/9799919799.2024edition/functions/pthread_join.html)。
